# Audyt repozytoriów — 2026-09-16

## Werdykt

Oba projekty są wartościowymi laboratoriami, ale żaden nie jest gotowym
systemem produkcyjnym ani dowodem przewagi bukmacherskiej. `Model-buk-2.0`
wnosi dojrzalszy backtesting i uczciwe raportowanie wyników negatywnych.
`Model-BUK-MK` wnosi szerszy backend v0.5, integrację live i więcej rynków,
lecz te rynki nie przeszły pełnej walidacji.

## Najważniejsze problemy wykryte w obu repozytoriach

1. Czysty klon nie zawiera danych i artefaktów potrzebnych do predykcji.
2. v0.5 liczył EV brutto i nie uwzględniał podatku 12%.
3. ROI silnika rogów liczyło zysk zwycięzcy jako `odds - 1`, mimo że bramka
   używała EV po podatku.
4. v0.5 mógł emitować `BET` dla ręcznie ustalonych, niezwalidowanych baseline'ów.
5. Bieżące obserwacje API nie były odcinane względem kickoffu analizowanego
   meczu, co umożliwiało temporal leakage w analizach retrospektywnych.
6. Wybór metody de-vig oraz dyspersji/rozkładu częściowo wykorzystywał ten sam
   okres, na którym raportowano wynik.
7. Brakuje kontraktu `kickoff_at`, `known_at`, `fetched_at`, wersji źródła i
   niezmiennych snapshotów kursów.
8. „Confidence score” mierzył dostępność danych, nie skalibrowaną pewność.
9. Brakuje CI, lockfile, manifestu artefaktów, migracji DB i smoke testu czystego klonu.

## Zmiany wykonane podczas scalenia

- zachowano historię Git obu repozytoriów;
- na bazę badawczą `Model-buk-2.0` nałożono backend v0.5;
- przywrócono jawny `tax_multiplier` i `EV_net`;
- naprawiono zysk po podatku w referencyjnym backteście v0.2;
- domyślnie wyłączono `BET` dla niezwalidowanego v0.5;
- dodano cutoff i wykluczenie target fixture w obserwacjach live;
- zabezpieczono import FastAPI przy braku danych/modeli;
- przemianowano wynik operacyjny na `data_readiness` (pozostawiono alias
  `confidence` dla zgodności wstecznej);
- dodano testy regresyjne podatku, bezpiecznej bramki i cutoffu.

## Pozostałe blokery P0

- wyeliminowanie leakage przy doborze de-vig i rozkładu przez nested walk-forward;
- wersjonowany bootstrap danych i modeli z checksumami/licencjami;
- prediction-as-of także dla wszystkich artefaktów suite/registry;
- settlement rules dla push/void/Asian lines oraz profile bukmacherów;
- prospective shadow test na nietkniętym okresie.

Wyników historycznego ROI nie wolno używać marketingowo ani finansowo przed
ponownym przeliczeniem i walidacją prospektywną.
